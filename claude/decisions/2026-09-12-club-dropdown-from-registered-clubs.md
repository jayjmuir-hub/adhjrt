# The sign-up club dropdown is built from registered clubs the organiser has named, not a hardcoded list

**Ruling.** The team and player registration dropdowns are populated from the clubs that have completed the **club registration form** and been given an **official name** by an organiser — replacing the hardcoded `CLUB_NAMES` list (JRT-7). A club appears in the public dropdown only once it is **registered AND named AND not a rehearsal**; the gate is enforced **server-side**, never in the browser.

The pieces:

- **`netlify/functions/registered-clubs.js`** — a **public** GET (modelled on `registration-window.js`, *not* the organiser-gated `club-link.js`), returning **only** the official names. It joins the live club-registration records against the organiser's name map via `publicClubNames()` in `_regstore.js`, which reads only `row[CLUB_COLUMNS.indexOf('club')]`, uses the declared name as a lookup **key it then discards**, excludes rehearsals (the stored `record.rehearsal` flag, checked *before* the lookup) and superseded records (`listRecords` already drops them), dedupes case-insensitively and sorts. It **fails soft**: if either store read throws it returns `{ clubs: [], unavailable: true }`, never the declared names.
- **`netlify/functions/save-club-names.js`** — an **organiser-only** GET/POST storing one small `config` blob `club-names`: `{ v, rev, savedAt, savedBy, names: { <normalised declared name>: "<official name>" } }` — **names only, no contact detail**. Validates without coercing (a non-string officialName, a leading `= + - @`, a control char, or over-80 chars is refused), refuses to name a rehearsal, and treats **Clear as its own action** (a blank Save is refused, never a delete — the `club-link.js` doctrine). An **optimistic `rev` guard** returns 409 with the fresh map on a stale write; the client re-applies its one change and retries once.
- **The identity key is the existing `normaliseClubName`** (from `reconcileClubs` in `Organizer.dc.html`), copied to `_regstore.js` for the server and **drift-tested** (`test-club-name-drift.js`) so the Clubs tab, the naming and the public join agree by construction — no second normaliser.
- **`Organizer.dc.html` Clubs tab** gains a "Sign-up name" column (input + Save + Clear + an *In the sign-up list* / *Hidden — not named yet* badge) per registered club; drafts are keyed by the normalised name and survive re-render; the map loads on tab open (like the club link). **`Quins JRT.dc.html`** fetches the list into `state.clubs` (via `scores-data.js loadClubs()`, cached only when non-empty so a failure retries), falls back to the bundled `CLUB_NAMES` so the dropdown is **never empty**, and the free-text "Other — my club isn't listed" escape hatch is **removed** from both forms (closed list). Every club name renders through DC `{{ }}` text, so a hostile declared/typed name is inert.
- **Sequencing is operational.** Team registration is opened (the existing single window) only once the organiser judges every club is in and named — there is no system-enforced "all clubs registered" gate, because there is no roster of *expected* clubs to measure completeness against.

**Why.** `CLUB_NAMES` was a hand-edited list, and the ticket's real worry was that club names lived in several places that could silently drift, so a club could look under-registered. Sourcing the dropdown from the declarations makes them the single source; making the organiser name each club means the public only ever sees a vetted name, and — because everyone picks from one list — the organiser's declared-vs-registered reconciliation stops depending on fuzzy free-text matching. One trusted person per club registers it, so each club is entered once; the maintainer chose organiser-curated official names (the larger option) over showing the raw declared spelling, and hidden-until-named over showing unnamed clubs, so the public list is always clean and approved.

**Against, and why it lost.**
- *Show the declared spelling (tidied), no curation* — the smaller build. Rejected by the maintainer: a sloppily-typed declaration would become the public label, and there would be no approval step keeping half-finished or test entries out of the public list.
- *Recompute a club list some other way, or reuse `get-registrations.js`* — rejected: `get-registrations.js` is organiser-gated and returns clubs **alongside** contact PII; a public endpoint must read and return names only, projected at the source, so a forgotten field cannot leak. The leak sweep test plants a sentinel in every personal field and proves none escapes, including on the outage path.
- *A brand-new `normaliseClubKey`* — rejected: it would be a second, weaker normaliser disagreeing with the Clubs tab's own on suffixes/punctuation, a silent seam on one screen. Reusing the tested `normaliseClubName` (one Node copy, drift-tested) makes the four sites agree.
- *Per-key sub-blobs for true concurrency safety* — deferred: Netlify Blobs has no compare-and-set, so the single-blob `rev` guard is **optimistic, not atomic** — a few-ms TOCTOU window remains if two organisers save the same instant. Accepted for a couple of organisers who work sequentially; per-key sub-blobs (at the cost of a `store.list()` on every public read) is the escalation path if concurrent editing ever becomes real.
- **Accepted, known costs.** (1) During a fetch outage the dropdown shows the bundled `CLUB_NAMES`, so a *newly* registered club not in that fallback is unselectable until the fetch recovers (mitigated by the on-open retry and keeping `CLUB_NAMES` roughly current — do **not** delete it). (2) If a club re-registers under a genuinely different spelling (not a case/space/punctuation/suffix variant), its official name orphans and it drops from the public dropdown until re-named — it shows as *Hidden — not named yet* on the Clubs tab, so the organiser can see it, but there is no louder alert (no stable club id exists to re-point automatically). (3) Two real clubs differing only by a trailing `RFC`/`FC` would merge under one official name — this already happens in the Clubs-tab reconcile view and needs a stable club id to split; confirmed not a case among the current clubs. A server-minted stable club id would fix (2) and (3) and is a separate future ticket.

**Where in the code.** `netlify/functions/_regstore.js` (`normaliseClubName` + `CLUB_SUFFIX_RE` copy, `publicClubNames`), `netlify/functions/registered-clubs.js` (new, public read + join), `netlify/functions/save-club-names.js` (new, organiser write), `scores-data.js` (`loadClubs`), `organizer-data.js` (`clubOfficialNames` / `saveClubOfficialName` / `clearClubOfficialName`), `Quins JRT.dc.html` (`state.clubs` + `refreshClubs` + dropdown bindings; `__other__`/`clubOther`/`effClub` tombstoned), `Organizer.dc.html` (Clubs-tab "Sign-up name" control, `loadClubOfficialNames`, the save/clear/conflict-retry handlers). Tests: `tests/test-registered-clubs.js`, `tests/test-save-club-names.js`, `tests/test-club-name-drift.js` (new), extended `tests/test-organizer-clubs.js`, plus `tests/runall.ps1` and `tests/_prove-registration.js`.

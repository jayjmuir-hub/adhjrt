# One login can be an organiser AND the named manager of an age group, carried as an identity-only `manages` list that never gates access

**Ruling.** A dual account is an ordinary **`role:'organizer'`** account carrying a new **`manages: []`** array — the age-group ids it is the named manager of. `resolveSession` reads `manages` **live** from the stored account (like `role`, `ageGroupId`, `drawPools`/`drawTimes`), and it is **identity only: never consulted in any authorization decision.** An organiser is already a superset — `hasAgeGroupAccess` returns true for every group (`netlify/functions/_auth.js:249`) — so `manages` grants nothing; its only jobs are to steer the `/manager` default group, label the account as a group's manager, and feed a per-group roster. `hasAgeGroupAccess` and all ~20 server permission checks are **unchanged**, and the signed token stays single-role-shaped, so nothing new is trusted from the token (`sign()` never carries `manages`). Two organiser-only `accounts-admin` actions write it, mirroring `drawRights`: **`managerGroups`** (set the list, organiser accounts only) and **`setRole`** (promote a manager→organiser, folding the old `ageGroupId` into `manages`; or demote). A single **`managedGroupsOf(account)`** helper beside `hasAgeGroupAccess` is the only reconciliation of the two homes (a plain manager's `ageGroupId`, a dual organiser's `manages`), drift-tested; the per-group "Managers of {group}" roster derives from it. The `/manager` default group and a demoted organiser's re-route both read the **live account** (`my-account` verifySession), so they update without a manual sign-out — a role-change re-route, never a `sessionEnded` sign-out.

⚠️ **`setRole` promotion MUST delete the auto-approve markers** (`autoApproved`, `autoRevoked`, `suggestedAgeGroupIds`, `suggestedFrom`), exactly as `approve` does (`accounts-admin.js:236-239`). An auto-approved hub manager (Dan) promoted without this is auto-revoked on his next Club Hub sign-in: `hub-auth.js:154` fires on the surviving `autoApproved` flag with the now-deleted `ageGroupId`, dropping him to pending and signing him out. This is the one bug the design review caught; it is the risk centre of the build and has its own discriminating fault.

**Why.** Two real people no longer fit the mutually-exclusive `role` model: **Jay** is an organiser *and* the U16B manager; **Dan** is the U9 manager who now also helps run site admin. Because organiser access is a strict superset of manager access, dual-role grants **no new permission** — its value is only recognition (being listed as a group's manager) and the scoped `/manager` view. Keeping organiser-ness in the single `role` field means the permission core does not change at all: a reviewer confirms safety with one grep (`manages` never appears in an authorization predicate), and every one of the ~20 checks is already correct for an account that resolves to `role:'organizer'`. `resolveSession`'s live read (the guarantee `2026-09-11`'s session-rights card already relies on) makes every grant, promotion and demotion take effect on the next request. The roster, the live pre-select and the demotion re-route were built in full — over the minimal label-only / accept-a-re-login options — because the maintainer chose to do it properly rather than leave papercuts.

**Against, and why it lost.**
- *An inert field named `manages` is a standing temptation* for a future maintainer to wire into an access check — the exact bypass forbidden. Mitigated by a discriminating fault (a manager whose `manages` names another group still cannot access it) plus loud tombstones at the derivation and at `hasAgeGroupAccess`.
- *Two homes for "who manages group X"* (`ageGroupId` vs `manages`), reconciled only by `managedGroupsOf` + a drift test — discipline, not a mechanism.
- *`setRole` is a new access-mutating surface* the codebase deliberately avoided (`approve` never changes an existing role); it is the highest-consequence new action and carries its own guards, marker-cleanup and faults.
- **Approach 1 — manager-base account + an `alsoOrganizer` flag collapsed to the canonical role at `resolveSession`** (runner-up). Genuinely safe and avoids a role-mutating action, but it creates a **second source of organiser-ness** (`role==='organizer'` OR the flag) that every future check must honour and that must be taught to `hub-auth`'s auto-revoke — which our design leaves untouched because `role:'organizer'` is already protected there. Not self-symmetric (the mirror case needs a second field anyway).
- **Approach 3 — replace the scalar `role` with a `roles:[]` set everywhere** (rejected). The most conceptually coherent, but it rewrites the entire authorization layer in one atomic, un-rollback-able `main` deploy, breaking the exclusivity invariant several checks encode implicitly (`role !== 'manager'` *meaning* "is organiser") — a class of bug that greps clean. The highest-bypass, highest-churn way to serve two users who need only "organiser plus one group."
